# Device Monitor v2.15.0 — Email Log and release safeguards

## Changes

- **Email Log.** Services → Device Monitor → Email Log lists the notification attempts this node
  submitted, with time, node, type, recipient, subject and status. It provides search, type and
  status filters, Active/Deleted/All entries, pagination and UTC-labelled CSV export. Records live
  in `/var/db/devicemonitor/email_log.db`, separate from `devices.db`; 30-day retention is separate
  from the mail queue.
- **Message view and formatting.** The subject opens the existing message dialog. Captured bodies
  are shown as plain text with a complete delivery timeline under **Delivery details**. HTML is
  converted structurally: table label/value pairs stay on compact lines, paragraph breaks remain,
  scripts and remote images are removed and entities are decoded once. Existing stored bodies are
  not rewritten.
- **Status semantics.** Submission, queue, relay acceptance, failure and unknown are distinct.
  **Relay accepted** (DSN 2.0.0) means the relay accepted the message; it is not proof of inbox
  receipt. Out-of-band observation correlates the exact Message-ID with Postfix's own records,
  including dated log siblings when `latest.log` is stale.
- **Bulk soft deletion.** Local entries can be selected or removed from view; they remain
  restorable from the Deleted view until normal retention. Remote peer rows cannot be selected,
  deleted or restored. Mail queues and genuine messages are unaffected.
- **HA peer viewing.** Local, Peer and All nodes tabs use one shared table. Each row keeps its node
  identity and the role recorded when the message was sent. Peer access uses a dedicated read-only
  privilege for the peer page and message endpoints only; transport is HTTPS with verified trust.
- **Release and deployment safeguards.** An explicit candidate gate verifies source, archive
  identity, membership, required Email Log files and prior-stage acceptance before installation.
  Host acceptance is derived from generated execution records, and the supported order is `.23`
  testbed → `.252` BACKUP → `.253` MASTER. The release packages pristine core catalogue baselines
  and a supported catalogue-repair helper.
- **Price gate correction.** The development harness uses the provider's UTC premium windows with
  boundary regression tests.

## Upgrade

`install-unattended.sh` accepts 2.8 through 2.14.0 as predecessors. It preserves the existing
configuration and databases, reports `INSTALL_OK` with a rollback backup directory, and writes a
70-row install record plus generated core catalogues.

## Acceptance boundary

The installer and release tooling changed relative to the earlier accepted runtime archive. A fresh,
authorised sequential `.23` → `.252` → `.253` installation and generated acceptance is required for
this archive identity. Previous acceptance must not be transferred to a different archive.
